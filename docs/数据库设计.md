# 数据库设计 v0.1

SQLite，实体 SQL 在 `db/schema.sql`，种子在 `db/seed.sql`。初始化默认拒绝覆盖已有库，只有显式 `--reset` 才重建。

| 表 | 关键列/约束 | 用途 |
|---|---|---|
| area | id PK；parent_id 自引用 FK；area_type 枚举 | 区域组织树 |
| device | id PK；code UNIQUE；area_id/energy_type FK | 六块器具，基础负荷、单位、量程 |
| energy_type | code PK；单位；standard_coal_factor/carbon_factor | 两种能源与业务系数 |
| raw_data | id PK；device_id FK；(device_id,data_time) UNIQUE；value ≥0 | 小时消费量；质量 1/2/3；来源 METER/MANUAL |
| summary | 区域/能源/粒度/日期 UNIQUE；完整性计数 | 后续统计持久化 |
| alert | 器具/时间/类型/模型 UNIQUE | 后续异常预警 |
| forecast_result | 器具/粒度/预测时点/版本/生成时间 UNIQUE | 后续预测及区间 |
| collection_log | 写入数、时间范围、模式 | 第一周 bootstrap 证据，第二周回放日志 |

任务书的根区域 `parent_id=0` 在数据库存 NULL，避免引用不存在的 ID=0；公开接口 metadata 也返回 NULL，这一差异明确纳入契约。其他区域与器具 ID 保持示例。空压机房直接挂一车间、空调挂二车间、照明/水泵挂三车间，不虚构更多编号。

原始数据索引：时间范围、质量/器具/时间；唯一键同时服务器具时间查询。分页固定按时间、器具排序。生产数据最大值不硬编码在 raw CHECK 中，原因是历史异常可能超过量程，采集数据保留事实；手工填报应在 Service 层按 device.max_value 校验。量程 1000kWh/小时与100t/小时是演示校验假设，任务书未提供真实铭牌，第二周可维护，不能解释为设备实际规格。

原始表不保存 anomaly_truth，也不保存原始未破坏基线。truth 中的 original_value 仅供评价和生成验证。forecast/alert/summary 第一周空表，这是阶段边界，不制造预测、预警或模型指标。

外键确保引用完整性；未来区域更新需要业务层防循环，CHECK(id != parent_id) 仅防直接自引用。后续更新器具能源/单位必须校验一致；第一周仅只读与种子初始化。

一键重建：`python3 db/init_db.py --reset --import-data`。启动服务前执行，运行中的服务不可同时重建。数据不放入 Git 的 runtime DB，但两个 CSV 和生成报告随交付包提供，源码脚本也可重建。
